flowcast 예제 갤러리

데이터·설명을 주면 라우터가 다이어그램 단위로 쪼개고 drawer 서브에이전트가 병렬로 흐름도를 렌더링하는 Claude Code 플러그인. 아래는 3뷰의 합성 예제(실 데이터 없음)를 자체완결 HTML로 렌더한 라이브 데모다. 카드를 누르면 전체화면으로 열린다.

왜 이걸 만드는지, 어떤 문제에서 출발했는지는 블로그에 적었다 — 서비스는 움직이는데, 문서는 멈춰 있었다 ↗

sequence — 시간순 요청/응답 스윔레인 topology — 존 배치 + 번호 구간 component — 포트·프로토콜 방향 엣지

어떻게 동작하나

  1. 1입력확정된 흐름 문서·명세·설명·PPT를 준다. JSON을 손으로 짜지 않는다.
  2. 2라우터데이터를 다이어그램 단위로 쪼개고 각 단위의 뷰를 판별한다. 미결 단위를 해소해 manifest로 고정한 뒤에야 다음으로.
  3. 3drawer 병렬단위마다 서브에이전트가 뷰 스킬을 로드해 JSON→렌더·파일링. 한 요청에서 여러 그림을 동시에.
  4. 4취합·검토각 다이어그램에 근거가 된 원문 경로를 남겨, 검토하고 필요하면 다시 생성한다.

세 관점

하나의 프로젝트도 무엇을 알고 싶은지에 따라 필요한 그림이 다르다. flowcast는 질문에 맞는 관점을 골라 그린다.

sequence동작 — 무엇이 언제

요청과 응답이 어떤 순서로 오가는가. 행위자 사이 시간순 상호작용을 스윔레인으로.

topology실행 환경 — 어디를 거쳐

서비스가 어느 존과 인프라를 거치는가. 공간 배치 위에 요청 구간을 번호로 오버레이.

component구성 — 무엇과 무엇이

컴포넌트와 포트가 어떻게 연결되는가. 프로토콜 방향 엣지로 프로세스를.

JVM 동작 구조

클래스 파일이 JVM에 올라가 실행되기까지를 지도 한 장, 시퀀스 한 장, 메커니즘 다섯 장, 구동 애니메이션 한 장으로 나눴습니다. 1~7의 수치는 Amazon Corretto 21.0.1의 실행 출력과 JDK 소스에서, 8은 OpenJDK jdk21u 21.0.13 소스에서 가져왔어요. 지도에서 위치를 잡고 번호 순서대로 따라가면 됩니다.

component

JVM 1 | 런타임 구조 지도

javac가 만든 클래스 파일이 클래스 로더를 거쳐 메서드 영역에 올라가고, 인터프리터와 JIT, GC가 스레드별 영역과 힙을 쓰는 관계를 한 장에 담았습니다. 뒤의 카드는 이 지도의 화살표를 하나씩 확대해요.

전체화면 열기 ↗ JSON 소스
sequence

JVM 2 | java 명령부터 main까지

java -cp . Main부터 VM 생성, 초기화 없는 로딩, 리플렉션이 일으키는 검증, <clinit>, main, 처음 쓰는 순간의 지연 로딩까지입니다. 순서는 -Xlog:class+load,class+init 실출력과 LauncherHelper 소스를 따랐고, 메인 클래스를 못 찾는 예외 흐름도 한 장 더 있어요.

전체화면 열기 ↗ JSON 소스

JVM 3 | 클래스 로더 서고

JDK 21 내장 로더 3개가 클래스를 찾는 순서를 서고와 승강기로 그렸습니다. 이름 있는 모듈의 패키지는 부모를 거치지 않고 그 모듈의 로더로 곧장 가요(JDK 8식 부모 우선과 다른 점). 판단 순서는 JDI로 추적한 실제 로더 호출입니다.

전체화면 열기 ↗ 빌드 소스
mechanism

JVM 4 | 바이트코드 테이프 리더

javac 21.0.1이 만든 calc(3, 4)의 바이트코드 6개를 천공 테이프 리더가 한 칸씩 실행. 서랍 2칸은 locals=2, 스택 튜브 2칸은 stack=2 그대로이고, 리드아웃과 디스크 값은 javap 실출력으로 검증한 모델에서 나옴. 클릭이나 → 키로 한 칸씩 진행.

전체화면 열기 ↗ 빌드 소스
mechanism

JVM 5 | JIT 계층 변속기

한 메서드가 인터프리터에서 C1, C2로 올라가고 타입 가정이 깨져 deopt로 내려오는 과정입니다. 카운터는 정해진 간격마다 검사될 때만 판단에 쓰이고, 재컴파일은 C1을 건너뛰어요. 사건 순서는 -XX:+PrintTieredEvents 실출력 그대로입니다.

mechanism

JVM 6 | G1 영역 트레이와 피커

16MB 힙의 1MB 영역 16개에서 young GC가 살아 있는 객체를 Survivor로 복사하고 Old로 승격합니다. 임계 나이가 15, 15, 2로 바뀌어 배열이 나이 2에 Old로 가는 장면이 실측 그대로 나와요. 수치는 -Xlog:gc*와 mark word의 age 비트에서 읽었습니다.

전체화면 열기 ↗ 빌드 소스
mechanism

JVM 7 | 세이프포인트 신호 야드

System.gc() 전에 VM 스레드가 모든 자바 스레드를 세이프포인트에 세우는 과정입니다. 자바 코드를 달리던 스레드만 폴링 지점에서 멈추고, native, sleep, wait 스레드는 폴링 없이 safe로 세어져요. 순서와 수치는 -Xlog:safepoint=trace 1회 실행 기록입니다.

JVM 8 | java 명령부터 main 종료까지 애니메이션

구성도를 고정하고 main 스레드 표시점이 java -cp app.jar com.example.Main의 호출 34스텝을 따라 움직이며 무한 반복합니다. 구간 7개마다 쓰이는 구성 요소에 색이 켜져요. 링크가 validateMainClass의 리플렉션에서 일어나는 점은 JVM 2와 같고, 단계마다 jdk21u 소스의 함수와 줄 번호를 달았습니다. 이전, 다음, 속도 버튼과 Space, 화살표 키로 조작.

리눅스 동작 구조

사용자 프로세스가 커널을 거쳐 일하는 과정을 지도 한 장, 시퀀스 한 장, 메커니즘 다섯 장으로 나눴습니다. 수치는 모두 Docker Desktop VM의 Linux 7.0.14(arm64)에서 잰 실행 출력과 upstream 커널 소스에서 가져왔어요. 지도에서 위치를 잡고 번호 순서대로 따라가면 됩니다.

component

리눅스 1 | 커널 구조 지도

사용자 프로세스가 glibc와 시스템 콜 진입을 지나 VFS, 페이지 캐시, 블록 계층으로 내려가는 길과, fork가 메모리 관리와 스케줄러를 거치는 길을 한 장에 담았습니다. MMU는 커널 밖 하드웨어로 따로 두었어요. 뒤의 카드는 이 지도의 화살표를 하나씩 확대합니다.

전체화면 열기 ↗ JSON 소스
sequence

리눅스 2 | read() 한 번

read(3, buf, 4096)이 glibc, svc #0, el0_svc, vfs_read, filemap_read를 거쳐 돌아오기까지입니다. 페이지 캐시에 없을 때의 미리 읽기 요청, D 상태 잠듦, 완료 인터럽트, 깨어남은 ftrace 1회 기록 그대로예요. 잘못된 fd로 -9가 돌아오는 예외 흐름도 한 장 더 있습니다.

전체화면 열기 ↗ JSON 소스
mechanism

리눅스 3 | 시스템 콜 창구

x8에 번호를 싣고 svc #0으로 들어가면 커널이 472칸 표에서 핸들러를 골라 x0로 결과를 돌려줍니다. 입구는 번호와 상관없이 하나예요. 표 안 빈 칸, 표 밖 번호, 설정에서 빠진 번호가 모두 -38을 돌려주지만 서로 다른 길로 간다는 것을 ftrace 스택으로 확인했습니다.

전체화면 열기 ↗ 빌드 소스
mechanism

리눅스 4 | 4단 선반장과 카드 인덱스

48비트 주소를 9+9+9+9+12로 나눠 MMU가 4단 테이블을 걷고, 빈 칸이면 커널이 채운 뒤 다시 걷습니다. 빈 영역의 첫 fault는 L2에서 멈추고, 읽기만 하면 공용 zero page가 걸려요. TLB 적중은 VM에 PMU가 없어 재지 못했고, 그림의 카드 인덱스는 아키텍처 규칙만 따른 단순화입니다.

전체화면 열기 ↗ 빌드 소스
mechanism

리눅스 5 | EEVDF 레인 선택기

자격(lag ≥ 0)이 있는 태스크 가운데 가상 마감이 가장 이른 것을 고르는 과정입니다. nice 0, 1, 5 세 태스크의 슬라이스는 모두 약 3 ms로 같았고, 가중치는 얼마나 자주 뽑히느냐로만 나타났어요(점유율 46.9, 37.7, 15.5 %).

전체화면 열기 ↗ 빌드 소스
mechanism

리눅스 6 | 판을 나눠 쓰는 두 인쇄대

fork 뒤 부모와 자식이 같은 페이지를 쓰기 금지로 함께 쓰다가, 먼저 쓴 쪽이 복사본을 받고 남은 쪽은 복사 없이 재사용합니다. 재사용 판정은 혼자 매핑했는지가 아니라 참조 수가 1인지를 봐요. 그래서 첫 쓰기만 다른 CPU에서 한 실행에서는 쓰기가 모두 복사였습니다.

전체화면 열기 ↗ 빌드 소스
mechanism

리눅스 7 | 파이프 교환대

파이프 8개 중 2개에 데이터가 있을 때 poll()은 커널의 pipe_poll을 8번 부르고, epoll_wait는 ready 목록에 오른 2개만 다시 묻습니다. 1024개로 늘려도 epoll은 2번이에요. 등록 때 거는 콜백, ready 레인, LT 재삽입을 ftrace 횟수로 맞췄습니다.

전체화면 열기 ↗ 빌드 소스
